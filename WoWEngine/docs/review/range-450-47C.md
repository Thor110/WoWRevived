# Review: routines 0x450000-0x47CFFF (475 IDA procs)

**Counts: PORTED 227 · PARTIAL 45 · MISSING 11 · LIBRARY 192** (475 total; 0x462FF0, 0x4644C0, 0x464520 and 0x465700 are folded into other procs in the IDA listing and aren't counted).

Subsystems in this range: hand-written asm blitters, PolyLib and ISOLib (0x450130-0x457F14); WResearch (0x457F20-0x45BCB0); the research screen (0x45BCC0-0x45F770); WBuildList and the Build List window (0x45F770-0x462EE0); SoundFXSystem (0x462EF0-0x466E18); the MSVC CRT (0x466E30-0x477D00); the Reaper '95 FMV codec (0x477DC0-0x47AEF0); WLandscape (0x47AF10-0x47CC46); and the start of WObjectList (0x47CCF0-0x47CFFF). Docs/survey/part08-10.md already describe most of this. Their "missing" lists are out of date: research, production, the landscape and positional sound are now in the port.

## Missing

### AI (war map)
- **0x45A400 (Human) / 0x45B4E0 (Martian)**: the computer player's research choice. These are vtable slot +0x2C of WHumanResearch / WMartianResearch (vtables 0x4AAA78 / 0x4AAAA8, at .rdata 0x4AAAA4 / 0x4AAAD4), and the AI calls them at 0x442F10 (`call [edx+2Ch]` on dword_4E9B8C). On first use each one picks one of two hard-coded **research plans** with `rand() % count` (Human lists 0x4CA4F8 / 0x4CA580; Martian 0x4CA610 / 0x4CA6B0; the index is held in dword_4CA1A8 / dword_4CA364, -1 at start and not saved). It then starts the first item in the list that is in state 1 (0x45B860), and only falls back to 0x458A60 when no item in the list is available. The port calls the base 0x458A60 directly (`Research::ChooseForAi`, src/core/Research.cpp:323, from src/warmap/WarMapAi.cpp:186), so it never follows the plans. It also skips the extra rand() call, which shifts the game's random stream. *Task:* add `Research::ChooseForAiPlan` with the four lists (docs/survey/part08.md §2.7.3) and the per-session plan index, and call it from AiTurn.

### War map
- **0x460140 BuildList::CancelAll**: for an owner of class 1 (a constructor), it cancels every queue entry (each through 0x462120) and refreshes the window. There are two callers. The first is the war-map unit's 0x813D handler (0x428F75), which 0x439ED0 sends at 0x43A122 / 0x43A133 when a sector comes out of a battle without its command building (0x43C990). The second is 0x42A0B0, a war-map object being removed, reached from battle objects at 0x48D5C8 / 0x48DA78 / 0x495BE8. Nothing in the port handles 0x813D or cancels a constructor's queue. *Task:* add `WarMap::CancelFactory(ref)` (0x462120 on each entry) and call it from the sector-exit code (0x439ED0) and from object removal.
- **0x45F7D0 / 0x460A40, the counter tool tip's production lines**: the routines are trivial: the head's hours times the supply multiplier, and the head item's name. They are used only by the war-map unit tool tip 0x428D70 (0x42904D: `"\n%s %s\n%s %0.1f"` with texts 0x48E "Currently building", 0x48F "Days to completion", 0x493 efficiency through 0x460740; plus Idle / Construction suspended). src/warmap/WarMap.cpp:1194-1196 says outright that these lines are "not in yet". *Task:* add them to `WarMap::CounterTip`. (These two procs are counted as PARTIAL.)

### Sound
- **0x463C30 PickAmbient** (with the ambient part of the per-tick update 0x462FF0): ambient sounds are voiced only by the system update, which picks the loudest audible one. When it changes, the playing ambient voice fades out over 150 ticks and the new one fades in over 15 ticks (0x4655F0 overrides the requested fade-in). The port voices every ambient sound as soon as Play is called (src/platform/Sound.cpp:89-160) and has no crossfade. Engine sounds have the same problem: the original voices at most 4 of them from the update, the loudest silent one first. *Task:* add a per-tick voice hand-out for types 0 and 1 to `Sound::Update`.
- **0x4652B0 (speech branch) / 0x466D00 PushUnique**: the speech queue. A type-5 sound with opcode 6 goes into the queue at 0x5891E0. A duplicate id is refused, and the head plays only when no speech voice is playing (0x462FF0). FadeOutAll leaves the queue alone (0x464AB0). The port has no queue, and SoundTable doesn't keep opcode 6. It is already listed in TASKS.md Milestone 6. *Task:* do as TASKS.md says.
- **0x4654E0 ResumeOffset (virtual voices)**: a voice taken back later starts at `(age-start)·rate·2(·2)/30 mod size` (0x4657B0). The port never takes a voice back, because quiet voices are never dropped. *Task:* see TASKS.md "Virtual voices".
- **0x4646C0 / 0x465EB0 / 0x465EF0, the `[Sound]` settings**: "Minimum Audible Volume" (float, 0.05), "Search Libraries First" (bool, 0) and "Unload Limit" (int, 0). The port hard-codes 0.05 in Attenuation and doesn't read the other two. *Task:* read them in FrontEnd's settings and pass them to Sound / SoundLibrary.

### Battle map
- **0x47CEE0 WObjectList::OnMessage**: when a list receives 0x80A0 (destroy), it re-posts it to each member through 0x4355A0. The first delay is 30 ticks, and each later one adds `30 + rand()%30`, so the deaths are staggered. Every other message is forwarded to the members at once. 0x80A0 reaches a list from the war-map unit's 0x80AA / 0x8136 handler (0x4293FF posts it to its member list +0x4C). The port has no object lists and no stagger: nothing in src uses `% 30` for this. TASKS.md mentions the stagger only inside a [~] item. *Task:* when a group or unit list is destroyed as a whole, post 0x80A0 to its members with delays of 30, then +30+rand()%30 each.

## Partial / divergent

### Rendering (asm)
- **0x456DD0 Poly_DrawTriangle + 0x456CA0 edge set-up + the 12 16-bit span routines** (0x45336F, 0x453680, 0x4539C2, 0x453D54, 0x45411A, 0x454523, 0x4549AB, 0x454DD1, 0x45597E, 0x455D76, 0x4561F2, 0x456436, 0x4566FE, 0x45698D). The port has these as a *provisional* affine filler, src/core/WofView.cpp:268-310, and the code says so. Not copied: the edge interpolants in 16.16 / 8.8 through the reciprocal table word_4C10CC; the 252-row overflow abort (0x456CA0 sets dword_4C0BBC); the outcode rejection; and the per-mode span semantics (gouraud versus flat versus 16-bit 50% translucent, which uses the 0x4C0D08 mask at 0x455B00). Table 0x4C1EFC also shows that modes 2-3 (0x455276 / 0x45597E) and modes 4-7 (0x4561F2) repeat. See Bugs for the flat level. *Task:* trace the edge set-up and the three span families, and replace FillTriangle.
- The 8-bit spans (0x4515B2 ... 0x4555B8) are counted as LIBRARY, because the engine draws at 32 bits.

### Research
- **0x45BB90 Complete, the other side's notification**: for a non-local research, it sends 0x111 / 0xB9 with the type to that side's player (dword_4E9B78), whether notifications are on or off. The port declares `listener.otherSideCompleted` (src/core/Research.cpp:288), but WarMap builds the other side's research with an empty `Research::Listener{}` (src/warmap/WarMap.cpp:698), so nothing hears it. What the player object does with 0xB9 is outside this range and unclear. *Task:* trace the AI player's 0xB9 handler and wire the listener.
- **0x45A1C0 / 0x45B320 UpdateTriggers**: these are ported (src/core/Research.cpp:13-35, 372). The type ranges and the 17 `[Tweak]` defaults were checked against the pushes at 0x4592C0-0x459500 and 0x45A4C0-0x45A640 and match. But their input `WarMap::encountered` (src/warmap/WarMap.h:434) is never filled: nothing sets the unit table's +0xAC (0x47F630 / 0x488C00 / 0x492931). So no trigger ever completes, and the items that depend on triggers (for example "Reading Martian symbols", and the 0x45B8B0 preference in 0x458A60) stay locked. *Task:* set `encountered` from the battle map at those three places.
- **0x458460 Cheat_CompleteAll**: `Research::CompleteAll` exists (src/core/Research.cpp:398), but the cheat-key sequence 0x4013A0 that calls it isn't wired (see TASKS.md Cheats).
- **0x45ECB0 ResearchHotspot keys**: Up / Down post 0x8008 / 0x8007 to the parent. The port wraps round at the ends, which is marked *provisional* (src/frontend/ResearchScreen.cpp:316-317). *Task:* trace the parent's 0x8007 / 0x8008 (0x45E9E0: the next hotspot with flags bit 16 / bit 28) for the end behaviour.

### Build list
- **0x4601C0 / 0x460200**: the build commands go out as network command packets (0x16 with a 0x20-byte placement block, or 0x17; header 0x707 via 0x447D80 / 0x447DB0), so they come back one queue pass later. The port applies the order directly (src/warmap/BuildWindow.cpp:172-174). This is the same open point as TASKS.md "Commands one queue pass later" and "Network game".
- **0x462B50 / 0x462E50 / 0x462EB0, the cursors**: the item buttons set cursor 0xE (enabled) or 0xC (disabled), a queue slot sets 0xF, and the small buttons set 0x10 on hover. The Build List window has no cursors yet (TASKS.md "to do: cursors").
- 0x45F7D0 / 0x460A40: see Missing / War map.

### Sound
- **0x463640 AllocateSlot**: the limits, priorities and stealing match (src/platform/Sound.cpp:122-160). It doesn't reject a sound whose `volume·attenuation` is below the minimum (the original returns -1), and it steals engine voices by `gain·fade` rather than by audible volume. The second point is marked provisional in src/platform/Sound.h:8.
- **0x464CB0 SoundObject::Tick / 0x465940 Voice::Update**: not copied: the start delay (+0x24; only the research screen fakes one), sounds that go quiet losing their voice ("Shutting down quiet sound"; ambient fades out with keep-alive instead), voices taken back for explosions, weapons and special only at their start tick, and volume / pan written on alternate frames. Most of this is marked provisional in Sound.h.
- **0x464EB0 FadeOut / 0x464E80 FadeOutKeep**: the original keeps the earliest end: `end = min(end, age+n)` and `fadeStart = min(fadeStart, age)`. The port ignores a second FadeOut while one is already running (src/platform/Sound.cpp:181-186), and FadeOutAll restarts every fade with the new length (:188-193), so a fade can get longer. FadeOutKeep (the +0x50 keep-alive, used for ambient) is missing.
- **0x464FF0 Attenuation**: the formula matches (src/platform/Sound.cpp:57-70). Small differences: the original tests the rects with PtInRect, so right and bottom are exclusive (x = +320 is already outside the inner rect, while the port uses `abs(d) <= inner`); it returns 1 for samples without DSBCAPS_CTRLVOLUME (flag 0x80 on sample +0x1C); and it caches the last result by position only, regardless of type.
- **0x4644C0 / 0x4644F0 / 0x464520 / 0x464550 / 0x464580-0x464640, the border rects and their `[Sound]` settings** (Inner / Outer / Inner Ambient / Outer Ambient border): the port hard-codes the default rects and doesn't read the settings.
- **0x464B10 ScaleBorders**: on a mode change it scales one side of each rect by w/640 and h/480 (asymmetric). It doesn't matter while the engine stays at 640×480.
- **0x4655F0 Voice ctor**: the ambient fade-in forced to 15 ticks isn't copied (see 0x463C30).
- **0x4660A0 / 0x466910 / 0x466640, the sample lookup order**: in the original a loose file wins only when 0x466910 returns a *different* path. That happens only in debug / cheat mode (byte_4D12F4), and only for the side or language overrides `SFX\HUMAN\`, `SFX\MARTIAN\` and `VOX\<Language>\...`. Otherwise the libraries are searched first, and the loose `<name>.snd` is only the fallback at load time (0x466300). The port always tries the loose `SFX\<name>.snd` first (src/core/SoundTable.h:84-86). Unload Limit (0x466640) isn't read. This only matters for mods.

## Bugs

1. **WOF flat-shaded faces take the wrong vertex's light.** In the original, 0x456DD0 reads the base shade `([esi+40h] & 0xFC) << 6` (0x456DF5-0x456E00) from vertex 0 *in the order the caller passed* (0x410070 ← 0x49F1FD), before its index-only sort (0x456E23-0x456E53). All the flat span routines read that base (dword_4C0C80, for example 0x4515B2+0x156 and 0x45336F at 0x4534CB). The port sorts the points by y first (src/core/WofView.cpp:278) and then takes `flatLevel = p[0].shade >> 2` from the *topmost* vertex (src/core/WofView.cpp:279). The caller passes (a, c, b) (WofView.cpp:375-378), and in non-smooth pieces only `vertexLight[face[0]]` is set for the face (WofView.cpp:358). So a flat face whose top vertex isn't `a` is drawn with a light left over from another face. *Fix:* take the flat level from `pts[0]` before sorting.
2. **The computer player's research uses the wrong routine.** See Missing / AI. The AI's vtable +0x2C call resolves to 0x45A400 / 0x45B4E0, not 0x458A60. docs/RESEARCH.md:182 ("vtable +0x2C, 0x458A60") is wrong, and the port (src/warmap/WarMapAi.cpp:186 → src/core/Research.cpp:323) follows that doc.
3. Doc correction, not a port bug: docs/survey/part08.md §2.6 suggests the 16-bit 50% mask 0xFBEF (565) "lets the top bit of green leak". It doesn't. The spans shift 16-bit registers (`shr cx,1` / `and cx, word_4C074C` at 0x4511A6-0x4511B3), so bit 15 is always 0, and 0xFBEF clears exactly bits 10 and 4. The port's per-channel halving in src/frontend/Canvas.cpp:51 is the right equivalent.
4. docs/survey/part10.md task 11 says the game searches "libraries first". docs/survey/part09.md and the port say "loose first". Both are partly right: see Partial / Sound 0x4660A0. The port's comment in SoundTable.h:84 is inaccurate for non-debug play.
